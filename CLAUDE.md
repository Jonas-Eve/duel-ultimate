# CLAUDE CODE GUIDE & DIRECTIVES (MONOREPO ROOT)

## 1. OVERVIEW & SPECIFICATIONS REFERENCE
duel-ultimate — LCG (Living Card Game) en ligne, évolutif, que l'on fera grandir pour le rendre compétitif : des duels 1 contre 1 au tour par tour avec des decks préconstruits et équilibrés, sans booster ni collection. Chaque deck a des mécaniques réellement différentes ; le gameplay se travaille au fur et à mesure. Le moteur de règles est générique et indépendant du thème ; cartes, decks et extensions sont des données versionnées, et l'équilibrage est mesuré par un simulateur IA contre IA.

The functional scope is specified in `PROJECT-FUNCTIONAL-SCOPE.md`. Read it before
designing anything that touches product behavior.

## Architecture

Monorepo : un workspace Cargo (cœur en Rust) et une application web TypeScript. Le moteur est
**pur et déterministe** (`état + action → nouvel état + événements`, hasard issu d'une graine
portée par l'état) : il n'a ni I/O, ni horloge, ni dépendance au réseau. Le **serveur est
l'autorité** sur la partie et filtre l'information cachée envoyée à chaque joueur ; le client
ne décide jamais d'un résultat. Parties **anonymes** (par lien), en mémoire, joueur contre
joueur ou contre IA (l'IA réutilise le moteur côté serveur).

| Composant | Rôle | Stack |
|---|---|---|
| `crates/engine` | Règles : un seul tour continu, une règle de temps unique, invocation (`Action::Play { card, picks? }`, la carte passe de la main au plateau), effets de héros (dont la pioche), attaque du héros adverse (`Action::Attack { attacker, target: Target::Hero }` : coût `attack_cost`, dégâts `force` ; PV à 0 → victoire `HeroDown` sans passation) ou d'une créature adverse (`target: Target::Creature(id)`, JSON `{"creature":7}` : elle perd `force` PV (`stats.health` est la santé *courante*), meurt à 0 et va dans la défausse de son propriétaire (`GameState::discard`, publique, dans l'ordre de mort ; `creature_health` pour le plateau) ; dégâts excédentaires perdus, jamais de `HeroDown` ; événements `creature_damaged` puis `died`, avant le changement de joueur actif ; toute cible qui n'est pas une créature du plateau adverse — créature propre, main, pioche, défausse, id inconnu — donne la même erreur `target_not_on_board`, après le contrôle de l'attaquant), **provocation** (tant que l'adversaire a une créature à `provocation` sur son plateau, une attaque ne peut viser que l'une d'elles, le héros n'est pas ciblable ; refus `target_forbidden_by_provocation`, distinct de `target_not_on_board`, évalué après l'attaquant et après la présence de la cible sur le plateau adverse, donc sans fuite sur les zones cachées ; filtre unique `provocation_allows` appelé par `validate` seul, recalculé sur l'état courant, sans cache ; seule la provocation de l'adversaire contraint, une créature qui provoque attaque librement ; une créature morte ne provoque plus), **riposte simultanée** (une créature attaquée inflige sa `riposte` à l'attaquant **en même temps** que celui-ci lui inflige sa `force`, y compris si elle meurt de cette attaque ; les deux dégâts sont calculés sur l'état d'avant l'attaque par `plan_damage` (fonction pure de `combat.rs`) puis appliqués par `apply_damage`, étape isolée qu'un futur effet d'ordre de dégâts modifiera seule ; le héros n'a pas de riposte **option `hero_riposte` désactivée** (`RuleSet::legacy()` : une attaque sur le héros n'en déclenche alors jamais) ; **option active par défaut depuis #172** (`RuleSet::standard()` ; écrite à la main dans le setup : `RuleSet { hero_riposte: true, .. }`, #170), riposte « infinie » : un coup sur le héros qui ne le tue pas (`santé du héros > force`, lue avant l'attaque, décidé en un seul endroit par `plan_damage` : `AttackDamage.attacker_slain`) détruit l'attaquant quelle que soit sa santé : événement additif `hero_riposted { player, creature }` (`player` = propriétaire de l'attaquant, sans montant), après `damaged` et avant `died`, défausse publique de son propriétaire, coût d'attaque payé quand même (la passation et l'épuisement sont évalués ensuite) ; un coup létal reste `HeroDown`, ni riposte, ni mort, ni passation, `apply` ne change pas ; riposte 0 : aucun événement ni effet ; excédent perdu, soustractions saturées ; événement additif `riposted { player, creature, amount }`, `player` = propriétaire de l'attaquant, `creature` = l'attaquant, `amount` = riposte nominale de la cible ; journal d'une attaque : `attacked`, `damaged` (héros) puis `hero_riposted`? (option, coup non létal) ou `creature_damaged` puis `riposted`?, `died`* (tous les morts des deux camps, ordre d'identifiant d'instance croissant, quel que soit le camp ou le rôle, l'attaquant mort comme la cible), `game_won` (`HeroDown`, seulement sur le héros : alors ni riposte ni passation) ou `token_moved`, `active_player_changed`?, `game_won` (`Exhaustion`)? ; le coût d'attaque est payé même si l'attaquant meurt de la riposte ; l'épuisement est évalué après chaque attaque, y compris quand la riposte tue la dernière créature d'un joueur qui reste actif), `Concede`, épuisement (`check_exhaustion` = aucune action utilisable, par un itérateur paresseux : une créature qui porte l'attaque a toujours une attaque légale par attaquant — un provocateur adverse s'il y en a, sinon le héros adverse —, donc garde son joueur en vie ; une créature morte a quitté le plateau et ne compte plus ; reformulé par #131 en « si et seulement si la force effective est au moins 1 »), **actions dérivées des effets présents** (#183, `src/effects.rs`, types `pub(crate)`) : `effects_of(état, source)` est l'accesseur unique des effets d'une source (carte en main : `Play` ; créature du plateau : `Attack`, effet intrinsèque synthétisé, jamais une ligne de données, une créature ne déclare aucun effet ; héros : `Declared(i)`), `sources(état)` énumère paresseusement les `Use` candidats dans l'ordre des actions légales, `decode`/`encode` convertissent `Action` et `Use` (inverses), et `usable(état, &Use)` est le seul prédicat de légalité (mêmes contrôles et même ordre d'erreurs qu'avant, aucun contrôle de force : une force 0 construite à la main reste attaquante jusqu'à #131) ; `validate` = partie en cours, `TooManyPicks`, puis `usable` ; `legal_actions` = `sources` filtrés par `usable`, encodés, puis `Concede`  ; **valeurs effectives** (#185, `src/effects.rs`) : `effective(état, &CardInstance) -> EffectiveStats` (`pub(crate)`, `#[inline]`) est le **seul lecteur** du coût, de la force, du coût d'attaque, de la riposte et de la provocation (`provocation_allows`, `plan_damage`, coûts d'invocation et d'attaque de `resolve`, `card_view(état, carte)`) ; **identité à cette tranche** (copie les cinq champs de `card.stats`), #131 y replie les modificateurs sans toucher un appelant ; la santé courante (`stats.health`) reste lue directement, ce n'est pas une valeur effective ; gardé par `tests/effective_is_the_only_reader.rs`, un balayage de source du code de production de `crates/engine/src/*.rs` (texte avant le premier `#[cfg(test)]`, `testing.rs` ignoré, dans `effects.rs` seul le corps d'`effective` est exempté) qui interdit `.stats.(force|attack_cost|riposte|provocation|cost)` et `CreatureStats {` hors `setup.rs`/`state.rs`, avec un auto-contrôle (`the_scan_itself_reads_what_it_should`) ; **écriture par opération** (#184) : `apply` = `validate`, `decode`, puis `effects::resolve(état, &Use, événements) -> Settled` qui résout **par opération** (`Op` : `Draw { count }`, `Attack`, `Play`, construit à la volée depuis l'`EffectRef` ; `op_of` est l'unique normalisation du sucre du héros), dans le même ordre d'événements qu'avant ; `Settled::Spent(coût)` : `pay` puis `check_exhaustion` ; `Settled::Ended` (attaque létale sur le héros, abandon) : ni temps ni épuisement ; `plan_damage`/`apply_damage` (avec `resolve_damage` et `bury_dead`) sont l'implémentation de l'opération `Attack`, `combat.rs`, `time.rs` et `pay` inchangés, `time.rs` reste la seule règle de temps ; `legal_actions` (ordre : cartes en main, activations d'effets, puis une attaque par couple (attaquant, cible) : par attaquant dans l'ordre d'invocation, le héros adverse d'abord, puis chaque créature adverse dans l'ordre du plateau, jamais une créature propre ni une créature morte, au plus plateau × (1 + plateau adverse) ; face à un provocateur, seuls les provocateurs adverses sont listés, dans l'ordre du plateau, sans le héros ; enfin `Concede` ; `apply` accepte exactement ces actions et `Concede`) ; terminaison : le potentiel Φ (PV des héros + par carte PV courants, +2 en pioche, +1 en main) décroît strictement à chaque action (la provocation ne fait que restreindre les actions légales ; la riposte ne retire que des PV finis ≥ 0 de plus à une créature en jeu, sans jamais rien ajouter ; la riposte du héros retire en plus la santé courante restante de l'attaquant, entier fini ≥ 1, donc Φ décroît plus fort encore, et Φ n'est pas modifié ; la preuve est vérifiée sous les quatre combinaisons d'options), preuve dans `combat.rs` vérifiée par un test sur 250 parties au hasard ; les mécaniques des decks seront des briques composables, qu'un deck active ou non. `GameStarted` (premier événement de `new_game`) porte `data_versions`, copie opaque de `GameSetup.data_versions` (clé obligatoire du JSON de setup, jamais interprétée ni triée ; avant-dernière clé de l'événement, absente du JSON quand la liste est vide, suivie de `rules` : l'objet complet des options de la partie, absent quand elles sont celles par défaut du moteur ; les journaux sans versions ni options hors défaut restent identiques octet pour octet) ; **Options de règles** (`src/ruleset.rs`, feuille du graphe, réexportées : `RuleSet`, `RuleSetError`, `MAX_BOARD_LIMIT` = 30 = taille d'un deck) : `RuleSet { hero_riposte: bool, board_limit: Option<u32> }`, ensemble **fermé** (une option ajoutée = un champ + une décision dans `validate`, destructuré sans `..`), `Default` écrit à la main = `RuleSet::standard()` **depuis #172** (story #127 : riposte du héros active et limite de plateau `STANDARD_BOARD_LIMIT` = 5, valeur décidée par le propriétaire, ajustable par mesure à #135 ; le corps de `Default` est le seul endroit qui change) ; `RuleSet::legacy()` = « options désactivées » (`hero_riposte: false`, `board_limit: None`), **figé pour toujours** : un test qui veut le nouveau jeu épingle `standard()`, un test qui veut l'ancien épingle `legacy()`, un test indifférent suit `default()` ; **rupture assumée de la rejouabilité (#127, décision du propriétaire)** : un ancien journal rejoué avec les réglages par défaut ne redonne plus le même déroulé ; restent garantis les octets de `starter@1.0.0` / `1.1.0` (`starter_1_1_0_is_1_0_0_byte_for_byte`), l'enregistrement des options avec chaque partie et l'ancien comportement par `RuleSet::legacy()` ; **l'absence de la clé `rules` signifie « le défaut du moteur de la version qui rejoue »** (avant #172 : `legacy`, après : `standard`), donc toute partie conservée hors du dépôt doit porter la clé explicite (aucune partie n'est persistée aujourd'hui) ; JSON : objet complet ou partiel en entrée (champ absent = défaut du moment, `"board_limit": null` = aucune limite), champ inconnu refusé, sortie toujours complète ; `GameSetup.rules` optionnel (absent = défaut du moteur, `standard()` ; écrit seulement hors défaut, donc **toujours écrit pour `legacy()`**, objet complet après `data_versions` même quand cette liste est vide), `GameState::rules()`, `new_game` valide les decks puis `rules.validate()` (`board_limit` dans `1..=MAX_BOARD_LIMIT`, sinon `SetupError::InvalidRules`, code existant `invalid_setup`, aucun nouveau code) ; **cartes portées sans nouveau comportement** (#208) : la garde temporaire de #206 et #207 (`SetupError::Unsupported`) est retirée, `new_game` reçoit sorts, unités `immobile`, étiquettes et effets déclarés ; `CardInstance` garde `stats` et gagne `extras: Option<Arc<CardExtras>>` (`None` pour une unité simple, donc le clone par action de l'aperçu ne change pas de coût ; un sort a pour stats son coût et des zéros, vie nulle pour Φ) ; **prédicats uniques lus par `usable`** : `attack_blocker(état, &CardInstance)` (`attack_force_zero` quand la force effective, lue par `effective()` seule, est 0 ; une unité `immobile` n'a pas de force donc n'attaque jamais, sans que le moteur lise `immobile`, que #129 raisonnera ; ordre d'une attaque : attaquant, force, cible, provocation) et `play_blocker_of(état, siège, &CardInstance)` (un sort : `unsupported_effect`, une unité : `play_blocker`, `board_full`) ; **`unsupported_effect` est un code temporaire**, retiré par #129 à #131 : un sort n'est jamais jouable (ni listé, ni compté pour l'épuisement) et l'effet `activated` déclaré d'une unité du plateau n'est jamais résolu (autre indice ou autre déclencheur : `unknown_effect`, source hors plateau : `source_not_on_board`) ; un joueur qui n'a que des unités immobiles et rien d'autre est épuisé ; **garde de lecture** : `tests/engine_never_reads_names_or_tags.rs` interdit `.name` et `.tags` dans `crates/engine/src/` hors d'une liste blanche par champ, présentation seulement (`.name` : `view.rs`, `setup.rs`, `data.rs` ; `.tags` : `setup.rs`, `state.rs`, `view.rs`) ; **effet des options** : `hero_riposte` agit depuis #170 (voir la riposte du héros), `board_limit` agit depuis #171 (**limite de plateau** : `board_limit: Some(n)` et un plateau de `n` créatures ou plus refusent une invocation, `RuleError::BoardFull`, code `board_full`, comparaison `>=` donc robuste si un état construit à la main dépasse la limite ; **fonction unique** `play_blocker(state, seat)` de `rules.rs` (`None` partie finie, sinon `BoardFull` si le plateau **public** du siège a atteint la limite, jamais lu sur une main), appelée par `validate` (siège actif, branche `Play`, **après** `hand_position` : un identifiant inconnu, caché ou de la main adverse donne `card_not_in_hand`, même plateau plein) et par `player_view` ; `legal_actions`, `Observation::actions`, `preview_legal_actions` et l'épuisement suivent seuls, une carte refusée n'est ni listée, ni aperçue, ni offerte à l'IA, ni comptée comme jouable ; une créature morte libère une place ; la limite seule n'épuise jamais un joueur, un plateau plein dont une créature porte l'attaque, donc a toujours une attaque légale) ; aucune formule Φ ni hasard : la limite ne fait que restreindre les actions légales, comme la provocation (preuve de `combat.rs` amendée, test sur 250 parties sous les limites 1, 2 et 5) ; le défaut est `standard()` (riposte du héros, limite 5) depuis #172 ; `legacy()` reste figé pour rejouer ou mesurer l'ancien comportement (règles passées explicitement) ; **Cartes du setup** (#181, story #128) : `PlayerSetup.cards: Vec<CardSpec>`, type de `duel-cards` ; `new_game` revalide chaque carte (`validate_card_spec`, après la forme du deck puis les noms) ; `build_side` lit la variante et pose `CardInstance.stats` comme avant ; le JSON de setup du binding ne change pas d'un octet (`tests/setup_json_golden.rs`, jamais modifié dans la story) ; **Noms de cartes** : `PlayerSetup.card_names` (optionnel, absent = pas de noms, `skip_serializing_if` vide) est **parallèle** à `cards`, vide ou de longueur exactement `cards.len()`, chaque nom d'au plus `MAX_NAME_LEN` = 64 caractères ; `build_side` l'associe à la carte (`CardInstance.name`, `pub(crate)`) avant le mélange, donc le nom suit la carte dans toutes les zones ; présentation seulement : aucune règle, formule Φ ni tirage ne le lit, journaux d'événements identiques octet pour octet avec ou sans noms (`validate_side` : forme du deck d'abord, puis noms, puis stats). **Construction depuis les données** (`src/data.rs`, la seule implémentation, sans E/S ni panique) : `player_setup(deck, cards)` (héros, stats et noms via `resolve_deck_named`) et `game_setup_from_data(cards, decks, deck_one, deck_two, data_versions)` (cartes puis decks analysés par `duel-cards`, decks trouvés par identifiant strict, miroir permis, `data_versions` opaque), `DataError` aux codes `invalid_json` / `invalid_setup` / `unknown_deck`. **Vue par siège** (`src/view.rs`, pure, sans générateur ni E/S) : `player_view(&GameState, seat) -> PlayerView` (`PlayerView`, `OwnSide`, `OpponentSide`, `HeroView`, `CardView`, `GameResult`, `Serialize` seulement) ; deux types distincts, `OwnSide` (main du siège) et `OpponentSide` (aucun champ capable de porter la main adverse, seulement `hand_count`) rendent la fuite impossible par construction, les deux n'exposent la pioche qu'en `deck_count`, la vue ne contient ni générateur, ni graine, ni `data_versions` ; forme JSON figée (contrat du client) : clés en snake_case, sièges et `active` en `"One"`/`"Two"` (`PlayerId` n'a pas de `rename_all`, incohérence cosmétique assumée), `result` `null` ou `{"winner","reason"}` (`hero_down`/`exhaustion`/`concede`), `health` = PV courants (0 en défausse), `name` `null` sans noms, **champs additifs de `CardView` (#209)**, dans cet ordre figé après les huit d'origine : `kind` (`"unit"` | `"spell"`, toujours écrit), `immobile` (`true`, omis si faux), `tags` (chaînes brutes de la liste du jeu, omis si vide), `effects` (toujours écrit, éventuellement `[]`), puis `unavailable` (toujours en dernier, omis quand il est vide : une vue sans raison à donner n'ajoute que `kind` et `effects` à une unité simple) ; les valeurs numériques existantes restent toutes présentes et **effectives** (0 pour `force` et `attack_cost` d'un sort ou d'une unité immobile, 0 pour la vie d'un sort), aucune n'est optionnelle ; `effects` = lignes d'effet `EffectLine { index?, trigger, cost?, ops, picks }` (`ops` = l'`Op` des données aplati + `polarity` `bonus|malus|neutral`, dérivée de `Op::polarity` ; `picks` = `CardEffect::expected_picks`) ; **l'attaque normale est une ligne synthétisée à la lecture** (jamais écrite dans les données, valeurs lues par `effective`), en première position et **sans `index`**, au même format qu'une attaque spéciale, pour toute unité non immobile (absente d'un sort et d'une unité immobile), quelle que soit la zone visible ; les effets déclarés suivent, dans l'ordre des données, avec leur `index` (position dans la liste déclarée, futur champ `effect` d'un `Activate`) ; `unavailable` = le code d'erreur du moteur qui dit pourquoi la carte ne peut pas servir à son usage principal (même tableau de codes que les refus d'`apply`) : **par carte de la main du siège demandé** (`rules::play_blocker_of`, le prédicat de `usable` : `board_full` pour une unité, `unsupported_effect` pour un sort jusqu'à #130) et **sur les unités de mon plateau qui ont une ligne d'attaque** (`rules::attack_blocker` : `attack_force_zero` ; jamais une unité immobile, #129 lui donnera sa raison), `None` une fois la partie finie, jamais sur le plateau adverse, en défausse ni dans `OutcomeView` (`hand_known` et plateau : la raison n'est pas calculée sur l'état d'un essai à blanc) ; **pas de fuite** : la main adverse n'est pas dans `PlayerView`, donc ni ses étiquettes, ni son type, ni ses effets (l'`OpponentSide` ne porte que le plateau et la défausse, publics : leurs étiquettes et leurs effets le sont) ; la **règle de provenance** d'`OutcomeView` s'étend aux étiquettes, au type et aux effets (une carte arrivée de la pioche reste masquée, une carte déjà connue de la main garde les siens) ; `.tags` n'est lu que par `view.rs` (garde `engine_never_reads_names_or_tags.rs`) ; la vue n'authentifie pas le siège (le serveur l'appelle avec le siège de la connexion). Limite connue : `legal_actions` et les événements `drew` exposent les identifiants de la main du joueur actif (acceptable en local, à rédiger côté serveur). **Observation** (`src/observation.rs`, pure, #140) : `Observation::of(&GameState) -> Option<Observation>` (`None` si la partie est finie), la fenêtre du siège actif pour une IA ; champs privés, ni `Deref`, ni accesseur vers l'état, ni `Clone` : la signature est la garantie, comme `OwnSide`/`OpponentSide` ; `seat()`, `actions()` (`legal_actions` sans `Concede`, même ordre, calculée une fois à la construction, éventuellement vide) et `view()` (`player_view` du siège, calculée à la demande) ; paresseuse, n'authentifie rien ; **résultat d'action sans fuite** (#141) : `preview(i)` (l'`ActionPreview` de l'action d'indice `i` de `actions()`, `Concede` exclu) et `outcome(i) -> Option<ActionOutcome>` (`None` hors borne, jamais de panique ; un clone par appel, rien n'est évalué à la construction ; `ActionOutcome { preview, view_after: OutcomeView }`, `Debug, Clone, PartialEq`, sans `Serialize`, jamais exposé au binding), tous deux lus sur l'**unique essai à blanc** `dry_run` de `preview.rs` (partagé avec `preview_legal_actions`, dont la sortie reste identique octet pour octet) ; `OutcomeView` est un type distinct de `PlayerView` (vue du siège qui a agi après l'action) dont le côté propre `OutcomeOwnSide` porte `hand_known` (cartes déjà en main avant l'action et qui y restent) et `hand_unseen` (nombre de cartes arrivées de la **pioche**), sans aucun champ capable de porter une carte piochée (identifiant, nom et stats masqués) ; **règle de provenance, pas de différence de main** : les identifiants masqués sont ceux des `Event::Drew` de l'action, une carte revenue en main depuis le plateau ou la défausse resterait publique ; le côté adverse est l'`OpponentSide` ordinaire ; si `apply` refuse une action légale sur le clone, le résultat n'a aucune conséquence (aperçu vide, vue inchangée). **Risque connu, à rouvrir par #128/#130** (effet non résoluble, sorts sans cible valide) : `ends_game: exhaustion` après passation est évalué sur la main du futur joueur actif, aujourd'hui seulement par des comptes publics (test : le contenu de la main adverse ne change pas le résultat) ; **Aperçu du temps** (`src/preview.rs`, pur) : `preview_legal_actions(&GameState) -> Vec<ActionPreview>`, de même longueur et dans le même ordre que `legal_actions`, par **essai à blanc** : chaque action légale est rejouée par `apply` sur un clone de l'état (l'état réel et le générateur ne sont jamais touchés ; Règles propres à ce repo :
- **Une carte est une donnée, pas du code** ; une extension est un dossier versionné, et chaque
  partie enregistre les versions utilisées (équilibrage traçable ; **rejouabilité d'anciens journaux rompue depuis #172** (story #127, décision du propriétaire) : le défaut du moteur a changé, les octets de `starter@1.0.0` / `1.1.0` restent figés et `RuleSet::legacy()` redonne l'ancien comportement, la clé `rules` d'une partie n'étant omise que pour le défaut).

  `GameState::random_below`.

  workspace **sans features par défaut** (`default-features = false`) ; `rand::rng()`, `StdRng` et
  `OsRng` ne compilent donc pas, et `getrandom` n'est jamais tiré. Ne jamais activer
  `getrandom/wasm_js` : la CI échoue si `getrandom` apparaît dans l'arbre de `duel-engine-wasm`.

  stricte ; sinon le script échoue avec la commande d'installation exacte. `--print-version` imprime

## 3. CODING STANDARDS & GLOBAL RULES
- **New Framework/Dependency → Latest Compatible Version:** when introducing a new
  framework or library (not bumping an existing one), pin the latest stable release
  compatible with the app's runtime — check the registry (`npm view <pkg> version`,
  `pip index versions <pkg>`) rather than guessing or reusing an older version from
  memory. Existing dependencies keep their current upgrade cadence; this rule is about
  the version picked at introduction time.
- **Clean Architecture:** Strict dependency isolation between Domain, Use Cases,
  Adapters, and Infrastructure across all services.
- **Security:** Never log secrets or tokens. Inter-service calls that cross a trust
  boundary require an explicit shared secret or equivalent, never an implicit trust
  assumption.

## 5. GIT WORKFLOW
- **Commit Freely On A Work Branch, Never On `main`:** on a short-lived work branch,
  committing and pushing completed work is authorized by default. On `main`, never commit
  or push without the user explicitly asking in the current task.
- **Amend, Don't Stack, Within The Same Not-Yet-Merged Context:** commits on a work
  branch exist to separate distinct contexts. If a new commit only fixes, corrects, or
  completes the change the immediately preceding commit made (not yet merged into `main`),
  amend that commit instead of adding a separate commit for the same context. Once a
  commit has merged into `main` (or a review has already landed on it), it's shared
  history — never amend or force-push it. A branch is also "shared" the moment another
  branch is created from it, even before either merges into `main`.
- **Trunk-Based Development:** `main` is the single trunk. Work happens on short-lived
  branches created from `main` and merged back quickly — no long-lived feature or release
  branches.
- **Conventional Commits:** Every commit message follows `type(scope): description`
  (e.g. `fix(backend): resolve null pointer in session lookup`). Common types: `feat`,
  `fix`, `docs`, `refactor`, `test`, `style`, `chore`. `scope` is typically the affected
  app, or omitted for repo-wide changes.
- **Squash Merge By Default, Rebase Merge For Deliberately Separate Commits:** squash a PR
  into `main` as one commit unless it carries multiple commits that are each independently
  meaningful on purpose (not fixups of an earlier commit in the same PR — those should have
  been amended per the rule above) — rebase-merge those instead, to keep them distinct in
  `main`'s history. Never a merge commit either way, and never force-push `main`.
