# CLAUDE CODE GUIDE & DIRECTIVES (MONOREPO ROOT)

## 1. OVERVIEW & SPECIFICATIONS REFERENCE
duel-ultimate — LCG (Living Card Game) en ligne, évolutif, que l'on fera grandir pour le rendre compétitif : des duels 1 contre 1 au tour par tour avec des decks préconstruits et équilibrés, sans booster ni collection. Chaque deck a des mécaniques réellement différentes ; le gameplay se travaille au fur et à mesure. Le moteur de règles est générique et indépendant du thème ; cartes, decks et extensions sont des données versionnées, et l'équilibrage est mesuré par un simulateur IA contre IA.

The functional scope is specified in `PROJECT-FUNCTIONAL-SCOPE.md`. Read it before
designing anything that touches product behavior.

## Architecture

Monorepo : un workspace Cargo (cœur en Rust) et une application web TypeScript. Le moteur est
**pur et déterministe** (`état + action → nouvel état + événements`, hasard issu d'une graine
portée par l'état) : il n'a ni I/O, ni horloge, ni dépendance au réseau. Le **serveur est
l'autorité** sur la partie et filtre l'information cachée envoyée à chaque joueur ; le client
ne décide jamais d'un résultat. Parties **anonymes** (par lien), en mémoire, joueur contre
joueur ou contre IA (l'IA réutilise le moteur côté serveur).

| Composant | Rôle | Stack |
|---|---|---|
| `crates/engine` | Règles : un seul tour continu, une règle de temps unique, invocation (`Action::Play { card }`, la carte passe de la main au plateau), effets de héros (dont la pioche), attaque du héros adverse (`Action::Attack { attacker, target: Target::Hero }` : coût `attack_cost`, dégâts `force` ; PV à 0 → victoire `HeroDown` sans passation) ou d'une créature adverse (`target: Target::Creature(id)`, JSON `{"creature":7}` : elle perd `force` PV (`stats.health` est la santé *courante*), meurt à 0 et va dans la défausse de son propriétaire (`GameState::discard`, publique, dans l'ordre de mort ; `creature_health` pour le plateau) ; dégâts excédentaires perdus, jamais de `HeroDown` ; événements `creature_damaged` puis `died`, avant le changement de joueur actif ; toute cible qui n'est pas une créature du plateau adverse — créature propre, main, pioche, défausse, id inconnu — donne la même erreur `target_not_on_board`, après le contrôle de l'attaquant), **provocation** (tant que l'adversaire a une créature à `provocation` sur son plateau, une attaque ne peut viser que l'une d'elles, le héros n'est pas ciblable ; seule la provocation de l'adversaire contraint, une créature qui provoque attaque librement ; une créature morte ne provoque plus), **riposte simultanée** (une créature attaquée inflige sa `riposte` à l'attaquant **en même temps** que celui-ci lui inflige sa `force`, y compris si elle meurt de cette attaque ; les deux dégâts sont calculés sur l'état d'avant l'attaque par `plan_damage` (fonction pure de `combat.rs`) puis appliqués par `apply_damage`, étape isolée qu'un futur effet d'ordre de dégâts modifiera seule ; le héros n'a pas de riposte, une attaque sur le héros n'en déclenche jamais ; riposte 0 : aucun événement ni effet ; excédent perdu, soustractions saturées ; événement additif `riposted { player, creature, amount }`, `player` = propriétaire de l'attaquant, `creature` = l'attaquant, `amount` = riposte nominale de la cible ; journal d'une attaque : `attacked`, `damaged` (héros) ou `creature_damaged` puis `riposted`?, `died`* (tous les morts des deux camps, ordre d'identifiant d'instance croissant, quel que soit le camp ou le rôle, l'attaquant mort comme la cible), `game_won` (`HeroDown`, seulement sur le héros : alors ni riposte ni passation) ou `token_moved`, `active_player_changed`?, `game_won` (`Exhaustion`)? ; une créature morte a quitté le plateau et ne compte plus), `legal_actions` (ordre : cartes en main, activations d'effets, puis une attaque par couple (attaquant, cible) : par attaquant dans l'ordre d'invocation, le héros adverse d'abord, puis chaque créature adverse dans l'ordre du plateau, jamais une créature propre ni une créature morte, au plus plateau × (1 + plateau adverse) ; face à un provocateur, seuls les provocateurs adverses sont listés, dans l'ordre du plateau, sans le héros ; enfin `Concede` ; `apply` accepte exactement ces actions et `Concede`) ; terminaison : le potentiel Φ (PV des héros + par carte PV courants, +2 en pioche, +1 en main) décroît strictement à chaque action (la provocation ne fait que restreindre les actions légales ; la riposte ne retire que des PV finis ≥ 0 de plus à une créature en jeu, sans jamais rien ajouter), preuve dans `combat.rs` vérifiée par un test sur 250 parties au hasard ; les mécaniques des decks seront des briques composables, qu'un deck active ou non. `GameStarted` (premier événement de `new_game`) porte `data_versions`, copie opaque de `GameSetup.data_versions` (clé obligatoire du JSON de setup, jamais interprétée ni triée ; avant-dernière clé de l'événement, absente du JSON quand la liste est vide, suivie de `rules` : l'objet complet des options de la partie, absent quand elles sont celles par défaut du moteur ; les journaux sans versions ni options hors défaut restent identiques octet pour octet) ; ## 5. GIT WORKFLOW
- **Commit Freely On A Work Branch, Never On `main`:** on a short-lived work branch,
  committing and pushing completed work is authorized by default. On `main`, never commit
  or push without the user explicitly asking in the current task.
- **Amend, Don't Stack, Within The Same Not-Yet-Merged Context:** commits on a work
  branch exist to separate distinct contexts. If a new commit only fixes, corrects, or
  completes the change the immediately preceding commit made (not yet merged into `main`),
  amend that commit instead of adding a separate commit for the same context. Once a
  commit has merged into `main` (or a review has already landed on it), it's shared
  history — never amend or force-push it. A branch is also "shared" the moment another
  branch is created from it, even before either merges into `main`.
- **Trunk-Based Development:** `main` is the single trunk. Work happens on short-lived
  branches created from `main` and merged back quickly — no long-lived feature or release
  branches.
- **Conventional Commits:** Every commit message follows `type(scope): description`
  (e.g. `fix(backend): resolve null pointer in session lookup`). Common types: `feat`,
  `fix`, `docs`, `refactor`, `test`, `style`, `chore`. `scope` is typically the affected
  app, or omitted for repo-wide changes.
- **Squash Merge By Default, Rebase Merge For Deliberately Separate Commits:** squash a PR
  into `main` as one commit unless it carries multiple commits that are each independently
  meaningful on purpose (not fixups of an earlier commit in the same PR — those should have
  been amended per the rule above) — rebase-merge those instead, to keep them distinct in
  `main`'s history. Never a merge commit either way, and never force-push `main`.
